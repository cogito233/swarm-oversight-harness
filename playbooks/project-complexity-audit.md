# Playbook · 项目复杂度必要性审计

> **定位**：用于诊断一个 AI 驱动的软件、研究、benchmark 或数据生产项目中，哪些复杂度是目标与信任链真正要求的，哪些是架构选择、过早泛化、控制面债务或规模冲动制造的；产出是删减与固化决策，不是再设计一套更大的平台。
>
> **核心原则**：逐项证明复杂度，不整体为系统辩护。删除、合并、手工化和延后优先于新增抽象；但不能以“简化”为名删除保护 headline claim 的信任边界。

## 适用时机

当出现以下任一情况时使用：

- 系统“能跑”，但必须有人持续值班；
- stage、队列、artifact 和配置不断增加；
- 做了很久仍主要在维护项目，而不是产出结论或交付；
- 不确定某个 sandbox、verifier、judge、服务或中间层是否必要；
- 想扩大吞吐，但未知失败和人工介入仍很多；
- AI 让新增组件很便宜，维护和理解却越来越累；
- 想判断应该 solidify 现有系统，还是退回 golden path / micro-batch。

## 使用方法

1. 把下面的 **诊断 Prompt** 交给能只读访问项目 repo、运行记录和设计文档的 agent。
2. 尽量提供目标与证据材料；缺失时允许 agent 先做只读盘点，但不允许它从代码形状反推项目目标后直接下结论。
3. 第一轮只做审计，不改代码。人先签字决定“删 / 合 / 延 / 留 / 固化”，再为采纳项开独立 SPEC。
4. 对高风险删除建议，要求一个小规模 ablation 或 shadow run，而不是凭直觉直接拆。

### 最小输入包

至少提供：

```text
项目根目录：
项目北极星 / 当前要回答的问题：
最终产物及其使用者：
最重要的 headline claim 或成功标准：
当前 pipeline 的入口与出口：
最近一次代表性 run 的日志 / manifest / summary：
当前最消耗人工注意力的 3 件事：
```

最好再提供：

- CHARTER / SPEC / STATE / DECISIONS；
- stage 定义、CLI 入口、schema、artifact 示例；
- 10–50 个 item 的小批运行统计；
- failure taxonomy、重试和 quarantine 记录；
- 人工介入次数与耗时；
- 最终论文、benchmark 或产品 claim 所需的信任链。

## 诊断 Prompt（可直接复制）

```text
你是一个“项目复杂度审计员”，不是架构炫技顾问。请对这个项目做只读审计，回答：当前存在的 stage、服务、队列、状态、artifact、配置、验证器和人工监督中，哪些复杂度是必要的，哪些可以删除、合并、手工化、延后，哪些虽然必要但实现得不够 solid，正在把运营责任外包给人的注意力。

你的目标不是把系统改得最优雅，也不是默认推荐 Airflow、Kubernetes、微服务、event bus、通用插件系统或重新平台化。默认偏好：删除 > 合并 > 使用现有机制 > 小型显式状态机 > 新基础设施。AI 让写代码变便宜，不代表长期拥有代码变便宜。

【项目输入】
- 项目根目录：<PATH>
- 北极星 / 当前唯一研究问题：<填写>
- 最终产物与使用者：<填写>
- 最重要的 headline claim / 成功标准：<填写>
- 入口与出口：<填写>
- 代表性 run / 日志 / manifest：<填写路径>
- 当前最消耗人工注意力的 3 件事：<填写>
- 时间、算力、人员约束：<填写，尤其说明是否单人维护>

【工作规则】
1. 开始前先读取项目的 AGENTS.md / CLAUDE.md / README / CHARTER / SPEC / STATE / DECISIONS，以及与 pipeline 入口直接相关的文件。不要扫描无关目录。
2. 全程只读。不要编辑、重构、安装依赖、触发昂贵 run 或启动大规模评测。若需要实验来判定，写出最小 ablation 设计，不自行执行。
3. 把“最终目标需要某种保证”与“当前实现这种保证的方式”分开。某个保证必要，不代表当前 stage、服务或抽象必要。
4. 不接受“以后可能会用”“更通用”“更 scalable”“解耦更好”作为存在理由，除非有当前 workload、历史事故或已承诺需求的证据。
5. 也不要为了简化而删除信任边界。若一个环节防止低频但会污染最终 benchmark / 论文 headline / 用户数据的失败，按期望损失评价，不按触发频率评价。
6. 每个判断必须引用 repo 路径、配置、日志、运行统计或明确的用户输入。事实、推断、未知分别标注。证据不足就写“未知”，不要补故事。
7. 如果项目目标本身不清楚、多个互相冲突，先报告“无法审计复杂度，因为目标函数未固定”，列出必须由人决定的最少问题；不要继续假装能判断必要性。
8. 区分“初建期合理的人工 failure-mode discovery”与“稳定期重复支付的 workflow debt”。第一次出现的未知错误可以人工处理；重复错误若仍靠人发现和恢复，就是控制面债务。
9. 审计的是 ownership cost，不是代码量。特别检查：谁记状态、谁发现失败、谁恢复、谁验证、谁承担静默污染、谁在三个月后理解它。
10. 不要用抽象形容词给建议。每条建议必须说明：删/合/延/留/固化什么，保护什么，牺牲什么，如何验证。

【第一阶段：重建目标与信任链】
先不要提出方案，先输出：
A. 一句话北极星。
B. 最终产物从“候选”晋升为“可信”的最小信任链。
C. 3–7 个必须被保护的 headline claims / invariants。
D. 明确 non-goals：当前不需要支持什么。
E. 如果用户没有提供上述信息，指出 repo 中的候选证据与冲突，但不要替用户悄悄决定。

【第二阶段：画出现状，而不是理想架构】
从实际代码和运行材料重建：
- stage DAG / pipeline：每一阶段的输入、输出、成功判据、失败去向；
- 状态所有权：每个 item 的 authoritative state 在哪里；
- artifact lineage：source、commit、config、pipeline version、输出如何关联；
- 控制面：调度、重试、恢复、quarantine、告警、人工 gate；
- 信任边界：哪些结果由同一个生成器自证，哪些有独立验证；
- 人工中断点：人的每次介入为什么发生、是否改变决策。

用一个简洁图和表格表示。若同一状态有多个来源，或状态只存在于 terminal / 人脑，明确标红为“状态债务”。

【第三阶段：逐项分类复杂度】
对每个 stage、长期服务、队列、artifact/schema、主要状态、配置维度、验证器和人工 gate，归入以下一类：

1. ESSENTIAL：目标或信任链本质要求；删除会破坏明确 claim。
2. ACCIDENTAL：保证可能必要，但当前拆分、接口或实现方式造成额外复杂度。
3. SPECULATIVE：为未发生、未承诺的未来需求而泛化。
4. CONTROL_DEBT：数据面能跑，但缺状态、恢复、隔离、摘要，迫使人值班。
5. SCALE_INDUCED：只在当前或更大规模越过拐点后才必要；判断现在是否已到拐点。
6. UNKNOWN：证据不足，需最小实验或人工决策。

每项必须填：
- 名称与路径；
- 它服务的最终 claim；
- 它防止的具体 failure mode；
- 删除后的可观察后果；
- 当前发生频率或证据；
- 更便宜的替代机制；
- 分类与置信度；
- 建议动作：KEEP / DELETE / MERGE / MANUALIZE / DEFER / SOLIDIFY；
- 验证该动作的最小实验。

特别检查以下复杂度乘数：
- 是否存在只有薄转换逻辑却独立拥有状态的 stage；
- 是否重复构建相同 sandbox / environment；
- 是否有多个 scheduler、queue 或 database 共同拥有同一 item；
- 中间 artifact 是否反复转换格式；
- config 选项是否多于真实实验变量；
- 是否同时支持多个实际上没在用的 backend；
- 是否把一次性研究切片做成常驻平台；
- 下游是否已能检出上游单独 stage 所防止的同一错误；
- verifier 是否和 generator 同源、自证或可被 game；
- 是否因流式机器执行而错误地让人类注意力也流式中断。

【第四阶段：计算单人拥有成本】
不要只报 LOC。给出项目的“运营面积”盘点：
- stage 数；
- 每阶段状态数及总状态转换数；
- artifact / schema 类型数；
- 可识别 failure classes 与 unknown 数；
- 恢复路径数；
- in-flight item 峰值；
- 人工 gate 数；
- 每 100 个 item 的人工介入次数和分钟数（若数据缺失，标未知并建议如何采样）；
- 需要翻日志才能回答的关键问题数；
- bus factor 与关键隐性知识。

回答：
1. 当前系统是否能由一个人长期拥有，而不仅是短期跑起来？
2. 人当前主要在做高价值语义判断，还是充当数据库 / 状态机 / 调度器 / 告警器？
3. 如果维护者离开两小时、两天、两周，各会发生什么？
4. 哪三个复杂度项占用最多 supervisory attention，而非最多代码？

【第五阶段：提出三个版本，而非一个“大重构”】
给出三个可比较方案：

A. MINIMAL GOLDEN PATH
- 为回答当前唯一问题，最少保留哪些 stage 和信任边界？
- 哪些环节退回单命令、人工或 10-item micro-batch？
- 能删掉多少状态、artifact 和长期服务？

B. SOLID SOLO PIPELINE
- 保留当前必要能力，但补齐单人可拥有所需的最小控制面：单 item replay、持久状态、幂等/不可变 artifact、quarantine、summary、actionable alerts。
- 不引入超出当前 workload 的平台能力。

C. SCALE PATH（只有证据支持时）
- 哪个量化阈值越过后，才值得引入更重的调度、并发或基础设施？
- 写出触发阈值，不要写“以后规模大了”。

对三案分别比较：保护的 claims、预期 yield、人工分钟 / 100 items、静默污染风险、实现成本、长期拥有成本、可逆性。

【第六阶段：给出执行优先级】
只给最多 5 个动作，按以下顺序排序：
1. 可立即删除且不伤信任链的复杂度；
2. 可合并的 stage / 状态 / artifact；
3. 最该延后的泛化；
4. 最大的控制面债务；
5. 只有通过离岗测试后才允许的扩容。

每个动作写：
- 具体改动边界；
- 为什么现在做；
- 不做什么；
- 验收指标；
- 回滚方式；
- 它预计减少多少人工介入或状态空间。

【必须设计的验证】
1. 10-item micro-batch：统计 stage yield、failure taxonomy、人工介入次数/分钟、unknown 数。
2. 删除/合并 ablation：在同一小批 item 上只改变一个结构因子，不覆盖 headline 结果。
3. 两小时离岗测试：正常 item 继续，异常安全隔离，无静默污染，回来只看 summary 即可决策。
4. 恢复演练：在一个 stage 中途 kill，验证能从持久状态恢复且不覆盖已分析 artifact。
5. 信任链 spot-check：抽检 accepted items，确认简化没有让 generator 自证或让 verifier 漏掉关键失败。

【最终输出格式】
# 复杂度审计结论

## 1. Verdict
- 一句话：当前主要是必要复杂度 / 偶然复杂度 / 过早泛化 / 控制面债务 / 规模错配中的哪一种组合。
- 是否应该继续建设大系统、先 solidify、还是退回 micro-batch。
- 最高风险：静默错误风险与人工注意力风险各一条。

## 2. 目标与最小信任链
<目标、claims、non-goals、信任链图>

## 3. 现状图
<真实 stage DAG、状态与 artifact 所有权>

## 4. 复杂度台账
<逐项分类表，带路径、证据、动作与置信度>

## 5. 单人拥有成本
<运营面积、人工介入、离岗情景>

## 6. 三种目标形态
<Minimal Golden Path / Solid Solo Pipeline / Scale Path 对比>

## 7. 建议采纳的 5 个动作
<按优先级，可执行且可回滚>

## 8. 需要人拍板的问题
<只列真正改变目标或信任边界、无法由 repo 事实解决的问题>

## 9. 最小验证计划
<10-item batch、ablation、离岗与恢复测试>

最后附一个“删减摘要”：
- DELETE：
- MERGE：
- MANUALIZE：
- DEFER：
- KEEP：
- SOLIDIFY：

不要以“需要进一步研究”收尾。即使证据不足，也要明确列出：当前最合理的临时判断、缺失证据，以及获取证据的最小动作。
```

## 人类审阅 Prompt 输出时的四个反问

Agent 的审计也可能偏向它熟悉的架构风格。签字前再问：

1. **删掉的究竟是一个实现，还是一个信任保证？** 若是后者，替代机制在哪里？
2. **新增的控制面是否真的减少值班，还是又创造一个需要值班的系统？**
3. **所谓 scale 是否有当前数据支持的阈值，还是“未来可能”叙事？**
4. **建议是否让人工时间从状态跟踪迁移到语义判断？** 如果没有，复杂度只是换了位置。

## 通过标准

一次复杂度审计的产物只有在以下条件下才值得采纳：

- 每个保留项都能链接到最终 claim 或具体 failure mode；
- 每个删除项都有反事实和最小验证；
- 没有用更重的平台替换一个小问题；
- 明确区分了当前需要与未来触发阈值；
- 有可量化的人工介入基线；
- 计划包含离岗测试和恢复演练；
- 最终减少的是运营面积和 supervisory attention，而不只是 LOC。
